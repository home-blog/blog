## 쉬운 설명: 이 기능이 어떻게 돌아가나

```
[마이페이지 열기]
 화면 ─▶ 서버: 쿠키의 세션 번호로 "누구인지" 확인 (없으면 401 → 로그인 창)
         주소에 회원 번호를 넣지 않는다 → 서버는 항상 "로그인한 나"의 정보만 돌려준다

[내 정보 고치기]
 닉네임·소개 ─▶ 서버: 규칙 검사(닉네임 2~10자, 소개 0~100자)
                     닉네임 중복 확인 (탈퇴하지 않은 다른 회원 중, 소문자로 비교, 나는 빼고)
                     회원 표의 두 칸만 고친다 ─▶ "저장했습니다"

[비밀번호 바꾸기]
 현재·새·확인 ─▶ 서버: 칸 규칙 검사 ─▶ 잠겨 있나? ─▶ 현재 비밀번호 해시 비교
                     틀리면 실패 횟수 +1 (로그인 실패와 같은 칸, 5회면 10분 잠금)
                     맞으면 새 비밀번호를 BCrypt로 저장
                     세션 표에서 "나의 세션" 중 지금 세션만 남기고 모두 삭제 ─▶ 다른 기기는 다음 요청에서 401

[회원 탈퇴]
 체크 + 비밀번호 ─▶ 서버: 잠겨 있나? ─▶ 비밀번호 비교 (틀리면 같은 칸에 +1)
                     한 번의 묶음으로: 내 블로그·글·분류·내 블로그 안의 댓글·내 좋아요 삭제
                                        다른 사람 글에 단 댓글은 남김 ("탈퇴한 사용자"로 표시)
                                        회원 표에 탈퇴 표시(deleted_at)
                     나의 세션을 모두 삭제, 쿠키 만료 ─▶ 화면: 첫 화면에서 "탈퇴가 완료되었습니다"
```

## Summary

**주요 요구**: 로그인한 회원이 마이페이지에서 내 정보를 보고 닉네임·소개를 고치고(US1), 현재 비밀번호를 확인한 뒤 비밀번호를 바꾸며 다른 기기의 로그인을 끊고(US2), 비밀번호를 다시 입력하고 두 번 확인한 뒤 탈퇴한다(US3). 비밀번호가 바뀌면 알림 메일을 보낼지는 정하지 않았다(US4, 선택).

**기술 방향**: `001`과 같은 단일 서버(Spring Boot)가 모든 규칙을 검사한다. 마이페이지의 모든 주소는 **회원 번호를 받지 않고 세션의 회원(`users_id`)만** 쓴다. 비밀번호 확인 실패는 `001`이 만든 회원 표의 실패 횟수·잠금 칸에 **합산**한다. 다른 기기 끊기와 탈퇴 때의 로그아웃은 **PostgreSQL 세션 표에서 그 회원의 세션을 찾아 지우는 것**으로 한다(`상세/01`에서 확정). 탈퇴는 여러 표를 **한 번의 묶음(트랜잭션)** 으로 지운다. 이 기능은 Redis를 쓰지 않는다.

### Source Code

코드는 이 문서 저장소가 아니라 **프로젝트 저장소**에 만든다. 안의 구조는 `기술스택-아키텍처.md` 3.A의 **기능별 모듈**을 따른다. (모두 `가안`)

**Structure Decision**: `001`과 같이 화면과 서버를 나누는 **웹 애플리케이션** 구조이고, 서버는 기능별 모듈을 가진 **단일 서버**다. 탈퇴는 다른 모듈의 데이터를 지우므로 **각 모듈이 정해진 입구만 내놓고**, `user` 모듈이 그것들을 한 묶음으로 부른다. (확정: 단일 서버, 가안: 모듈 이름과 입구)
