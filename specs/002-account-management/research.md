## B. 이 기능에서 고른 기술과 이유 (모두 `가안`)

각 항목은 **Decision / Rationale / Alternatives** 순서입니다.

### B-1. "나만 볼 수 있다"는 주소에 회원 번호를 넣지 않는 것으로 지킨다 (FR-002, FR-029, SC-001)

- **쉬운 설명**: `/members/12/profile`처럼 주소에 회원 번호를 넣으면, 누군가 12를 13으로 바꿔 남의 정보를 보려 할 수 있습니다. 그래서 주소를 `/account`처럼 **"나"** 로만 만들고, "나"가 누구인지는 서버가 세션에서 꺼냅니다. 남의 계정을 가리킬 방법 자체가 없습니다.
- **Decision**: 마이페이지의 모든 요청(`/api/account/…`)은 회원 번호를 받지 않는다. 서버는 세션의 `users_id`로 회원을 불러오고, 그 회원이 **탈퇴하지 않았는지**도 확인한다. 로그인하지 않았으면 `401 UNAUTHENTICATED`(`001` 약속). 화면의 마이페이지 주소도 회원 번호 없이 하나(예: `/mypage`)로 둔다. 상태 `가안`.
- **Rationale**: 헌법 원칙 IV(권한은 서버), FR-029. 번호를 비교하는 검사를 빠뜨리는 실수가 생길 수 없다.
- **Alternatives**: 주소에 번호를 넣고 "로그인한 회원 == 주소의 회원"을 검사한다. 가능하지만 검사를 한 곳이라도 빠뜨리면 SC-001이 깨진다.

### B-2. 비밀번호 확인은 한 곳에서: 로그인·비밀번호 변경·탈퇴가 함께 쓴다 (FR-014, FR-018, FR-022, SC-003, SC-006)

- **쉬운 설명**: "잠겨 있나 확인 → 비밀번호 비교 → 틀리면 횟수 +1, 5번째면 잠금"을 세 군데에서 따로 만들면 하나만 고치고 나머지를 잊기 쉽습니다. 그래서 **하나의 "비밀번호 확인" 도구**를 만들어 세 곳이 함께 씁니다.
- **Decision**: `user` 모듈에 비밀번호 확인 서비스 하나를 두고, `001`의 로그인과 이 기능의 비밀번호 변경·탈퇴가 함께 쓴다. 순서(가안):
  1. 잠금 시각(`locked_until`)이 지났으면 횟수를 0으로 되돌린다. (CF-02-7과 같은 규칙)
  2. 아직 잠겨 있으면 **비교하지 않고** 거절하고 남은 시간을 알린다. 이 동안의 시도는 잠금 시간을 늘리지 않는다. (`001`과 같은 해석)
  3. BCrypt로 비교한다. 틀리면 DB에서 바로 `+1` 하고, 5가 되면 `locked_until = 지금 + 10분`. **5번째로 틀린 그 요청의 응답은 잠금 안내**다. (`001` 계약 6과 같음)
  4. 맞으면 다음 단계로 간다. 이때 횟수를 0으로 할지는 **`D-4`**.
- **상태 코드 주의**: 현재 비밀번호가 틀렸을 때 **`401`을 쓰지 않는다.** `001`의 약속에서 `401`은 "로그인하지 않았음 → 로그인 창"이라는 뜻이라, 화면이 엉뚱하게 로그인 창을 띄운다. `400 CURRENT_PASSWORD_MISMATCH`로 답한다. (contracts 3)
- **Rationale**: FR-018의 "합산"을 가장 단순하게 지킨다. `상세/01`의 "같은 실패 횟수 칸에 합산한다"(CF-15-14, 17)를 그대로 옮긴 것이다.
- **Alternatives**: 기능마다 따로 센다 → FR-018 위반.

### B-3. 닉네임 바꾸기의 중복 검사 (FR-007, SC-002)

- **Decision**: 규칙 검사(2~10자, 한글·영문·숫자)는 `001`과 같은 검사기를 쓴다. 중복은 "**탈퇴하지 않았고, 내가 아니며**, 소문자로 바꾼 닉네임이 같은 회원"이 있는지로 본다. 그래서 내 닉네임 그대로(또는 `Kim` → `KIM`처럼 대소문자만 바꾼 것)는 중복이 아니다. 동시에 두 사람이 같은 닉네임으로 바꾸면 DB의 중복 불가 규칙(`001` D-4의 소문자 + 탈퇴하지 않은 회원 규칙)이 한 건만 통과시키고, 나머지는 "이미 사용 중인 닉네임입니다"로 답한다. 상태 `가안`.
- **Rationale**: `001` D-4와 같은 규칙을 쓰므로 가입과 수정에서 결과가 같다.
- **참고**: 닉네임을 바꾸면 화면 위쪽에 보이는 닉네임이 바뀌어야 하므로, 저장이 끝나면 화면이 로그인 정보(`GET /api/auth/me`)를 다시 받는다. 세션에는 `users_id`만 있으므로 세션을 고칠 일은 없다.

### B-4. 소개 (FR-008)

- **Decision**: 0~100자를 서버가 검사한다. 비우면 비어 있는 값(`NULL`)으로 저장한다. 글자는 따로 제한하지 않고 **그대로 저장**하며, 화면에 보일 때는 React 기본 이스케이프로 글자로만 보인다(NF-07). 상태 `가안`.
- **주의 (구현 때 확인)**: "100자"를 무엇으로 셀지. Java의 문자열 길이는 이모지 같은 글자를 2로 셀 수 있고, PostgreSQL의 `VARCHAR(100)`은 글자 단위로 센다. 서버 검사를 **글자 단위(코드 포인트)** 로 맞추면 두 쪽이 어긋나지 않는다.
- 앞뒤 공백을 지울지는 명세에 없다. `001`의 이메일처럼 지우지 않고 **입력한 그대로** 둔다. (가안)

### B-5. 다른 기기 끊기: 회원 기준으로 세션을 찾아 지운다 (FR-020, SC-005)

- **쉬운 설명**: 세션 표는 "번호표 명부"입니다. 명부의 각 줄에 "이 번호표는 12번 회원 것"이라는 이름표를 붙여 두었으므로(`001`), 비밀번호를 바꾸면 **12번 회원의 줄 중에서 지금 쓰는 번호표만 남기고 모두 지웁니다.** 지워진 번호표로 온 요청은 "누구인지 모름"이 되어 `401`을 받고, 화면이 로그인 창을 띄웁니다.
- **Decision**: Spring Session JDBC의 "이름표로 세션 찾기" 기능으로 내 `users_id`의 세션 목록을 받아, **지금 요청의 세션 ID와 다른 것**을 모두 삭제한다. 지금 세션은 그대로 두므로 로그인 유지 기간(마지막 사용 후 7일, 로그인한 때부터 최대 30일)도 원래대로 이어진다. 상태: 방식 `확정`(상세/01), 세부 `가안`.
- **Rationale**: `상세/01`이 세션 방식을 고른 이유가 바로 이것이다(“그 사람의 명부 줄만 지우면 끝”).
- **Alternatives**: 회원 표에 "비밀번호 바꾼 시각"을 두고 요청마다 세션 시각과 비교한다. ERD 변경이 필요하고 만들 것이 늘어나서 쓰지 않는다.
- **위험**: 아래 R-1, R-2.

### B-6. 탈퇴는 한 번의 묶음으로, 정해진 순서대로 지운다 (FR-024, FR-027, SC-007)

- **쉬운 설명**: 탈퇴는 표 여러 개를 지우는 일입니다. 중간에 실패해서 "블로그는 지워졌는데 글은 남은" 상태가 되면 안 되므로, **모두 성공하거나 모두 취소되는 한 묶음(트랜잭션)** 으로 처리합니다. 팀 ERD에는 "부모를 지우면 자식도 자동으로 지움" 설정이 없으므로, **자식부터 순서대로** 지웁니다.
- **Decision**: 비밀번호 확인(B-2)이 통과하면 한 트랜잭션 안에서 [data-model.md](data-model.md) 3의 순서대로 지우고, 회원 줄에 `deleted_at`을 넣는다. 트랜잭션이 끝난 뒤 그 회원의 세션을 모두 지우고 쿠키를 만료시킨다. 쿼리는 모두 파라미터로 전달한다(문자열 이어 붙이기 금지, 헌법 IV). 상태 `가안`.
- **모듈 사이**: `blog`, `post`, `comment` 모듈이 각자 "이 회원(또는 이 블로그)의 것 지우기" 입구를 내놓고, `user` 모듈의 탈퇴 서비스가 그것들을 차례로 부른다. 글 삭제 규칙(CF-05-15: 글을 지우면 댓글·좋아요·태그 연결·이미지도 지움)은 `003`/`005`가 만든 것을 다시 쓴다.
- **Alternatives**: DB에 "자동으로 같이 지움(ON DELETE CASCADE)"을 건다. 코드가 줄지만 **팀 ERD를 고쳐야 하고**, 실수로 회원 줄을 지우면 모든 것이 사라질 수 있다. 쓰지 않는 것을 추천하되, 팀이 원하면 바꿀 수 있다.
- **탈퇴한 회원 줄은 지우지 않는다**: ERD의 `users.deleted_at`(soft delete)을 쓴다. 남는 댓글이 그 줄을 가리키기 때문이다. 이 부분이 `상세/02`의 가안과 부딪힌다 → **`D-1`**.

### B-7. 화면의 일로 두는 것 (FR-001, FR-009, FR-011, FR-023, FR-025, FR-026)

- 저장 버튼 잠금(바뀐 것이 없을 때), 저장하지 않은 내용 확인, 탈퇴 안내 목록, 체크박스, 최종 확인 창은 **화면이 한다.** 서버가 알 수 없거나(최종 확인 창), 서버가 막을 필요가 없는 것(같은 값 저장)이다.
- 서버가 보조로 지키는 것: 탈퇴 요청의 `agreed`가 참인지, 같은 값으로 저장 요청이 와도 오류 없이 처리하는지.

## C. 위험과 확인할 점

### R-1. 비밀번호는 바뀌었는데 다른 세션 삭제가 실패하면 (FR-020, SC-005)

- **무슨 문제인가**: 비밀번호 저장과 세션 삭제가 서로 다른 묶음이면, 비밀번호만 바뀌고 다른 기기는 계속 로그인된 상태가 될 수 있다. SC-005("100% 끊김")를 어긴다.
- **Decision (가안)**: 둘 다 같은 PostgreSQL에 있으므로 **한 트랜잭션 안에서** 처리하는 것을 먼저 시도한다. 세션 저장소가 바깥 트랜잭션에 같이 묶이는지는 **(구현 때 확인)**. 묶이지 않으면 "비밀번호 저장 → 세션 삭제" 순서로 하고, 삭제가 실패하면 오류로 답해 사용자가 다시 하게 한다. (다시 바꾸면 다시 지운다)
- **상태**: 위험으로 기록. [quickstart.md](quickstart.md) S-5에서 확인한다.

### R-2. 회원 기준으로 세션을 찾을 수 있는가 (FR-020, FR-027)

- `001`에서 세션의 이름표(principal)를 `users_id`로 정했다. Spring Session JDBC가 로그인할 때 이 이름표를 따로 저장해 두어야 "이 회원의 세션 목록"을 찾을 수 있다. 기본 설정에서 이름표가 **로그인한 회원의 이름(username)** 으로 저장되므로, 로그인 때 그 이름을 `users_id`로 맞춰야 한다. **(구현 때 확인)**
- 이것이 안 되면 다른 기기 끊기(확정)를 지킬 수 없으므로, **US2를 만들기 전에 가장 먼저 확인**한다.

### R-3. 탈퇴하는 동안 다른 기기에서 글을 쓰는 경우 (FR-024)

- 탈퇴 묶음이 글을 지운 뒤 블로그를 지우기 전에 다른 기기의 글쓰기가 끼어들면, 블로그를 지울 때 DB가 거절해 **탈퇴 전체가 취소**된다. (데이터가 반쯤 지워지지는 않는다)
- 드문 경우라 지금은 "잠시 뒤 다시 시도"로 충분하다고 본다. 막고 싶으면 탈퇴 시작 때 회원 줄을 잠그는(`FOR UPDATE`) 방법이 있다. (가안, `tasks`에서 검토)
- 탈퇴가 끝난 뒤에는 세션이 지워지고, B-1에서 탈퇴한 회원인지도 확인하므로 다른 기기의 요청은 `401`이다.

### R-4. 내 블로그에 다른 사람이 단 댓글도 함께 지워진다 (FR-023, FR-024)

- 명세의 삭제 목록은 "내 블로그, 글, 분류, **내가 쓴 댓글 중 내 블로그 안의 것**, 좋아요"다. 그런데 글을 지우면 그 글의 **모든 댓글**(다른 사람이 쓴 것 포함)과 다른 사람이 누른 좋아요도 지워진다(CF-05-15). 그래서 실제로는 다른 사람의 댓글도 사라진다.
- 블로그가 없어지므로 당연한 결과이고 명세와 부딪히지는 않는다고 본다. 다만 **탈퇴 안내(FR-023)에 적을지**는 명세가 정할 일이라, 바꿀 일이 생기면 명세부터 고친다.
- 반대로 **다른 사람 글에 단 내 댓글에 달린 남의 답글**은 그대로 남는다(내 댓글이 남으므로).

### R-5. 브라우저를 닫거나 새로고침할 때의 확인 문구 (FR-011, SC-009)

- 화면 안에서 다른 화면으로 갈 때는 우리가 만든 확인 창에 "저장하지 않은 내용이 있습니다. 나갈까요?"를 보여 줄 수 있다.
- 탭을 닫거나 새로고침할 때는 **브라우저가 자기 문구로** 묻고, 요즘 브라우저는 사이트가 정한 문구를 보여 주지 않는 것으로 알려져 있다. **(구현 때 확인)** 이 경우에도 "묻는다"(SC-009)는 지켜지지만 문구는 다르다.

### R-6. 닉네임을 바꿔도 블로그 이름은 그대로다 (FR-006)

- 블로그 이름은 가입 때 `{닉네임}의 블로그`로 만들어지지만(`003` FR-002), 그 뒤로는 블로그 주인이 따로 고친다(`003` US7). 그래서 **닉네임을 바꿔도 블로그 이름은 자동으로 바뀌지 않는다**고 해석했다. (가안)
- 블로그 주소에 닉네임이 들어가면 닉네임을 바꿀 때 주소가 바뀐다. 블로그 주소 모양은 `003`이 정하고, 이 기능은 블로그 번호로 바로가기를 만든다(contracts 1).

### R-7. 탈퇴 때 이미지 파일 (FR-024)

- `post_image` 표의 줄은 묶음 안에서 지우지만, **파일 자체**는 DB 밖(이미지 저장소, 위치 `미정`)에 있다. 트랜잭션이 끝난 뒤 파일을 지우고, 실패하면 기록만 남긴다(사용자에게 보이는 데이터는 이미 없다). 방법은 `003`/`005`의 글 삭제와 같게 한다.

### R-8. 잠겨도 지금 로그인은 유지된다 (FR-018)

- 잠금은 "비밀번호를 확인하는 일"(로그인, 비밀번호 변경, 탈퇴)만 막는다. 이미 로그인한 기기의 세션은 끊지 않으므로 마이페이지 보기, 글쓰기 같은 다른 일은 계속 할 수 있다. 명세에 없어서 `가안`으로 해석했다.

## D. 정해야 할 것 (선택지와 추천안, 사용자 결정 대기)

> 사용자가 고르기 전에는 확정하지 않습니다. 고르면 이 표와 `plan.md`의 해당 줄을 같이 고칩니다.

### D-1. 탈퇴한 회원 줄과 남는 댓글의 작성자 표시를 어떻게 할까 — `미정`

- **문제**: `상세/02`의 `구현 방식`("미리 정해 둔 것", 가안)은 "다른 사람 글에 단 댓글은 **작성자 칸을 비워 두고** '탈퇴한 사용자'로 표시 (DB에서 작성자 칸이 비어도 되게 설계)"라고 적었다. 그런데 **팀 ERD의 `comment.users_id`는 `NOT NULL`** 이라 비울 수 없다. 반면 ERD의 `users`에는 이미 `deleted_at`(탈퇴 표시)이 있고, `001` D-4도 "탈퇴한 줄이 남아 있다"는 전제로 정했다. **지금의 가안은 팀 ERD를 고치지 않으면 지킬 수 없다.**

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 회원 줄을 남기고 댓글은 그대로** | 회원 줄에 `deleted_at`만 넣는다. 댓글은 그 줄을 계속 가리키고, 화면은 "작성자가 탈퇴했으면 '탈퇴한 사용자'"로 보여 준다 | **ERD를 안 고친다.** `001` D-4(탈퇴하지 않은 회원에게만 중복 불가)와 맞는다. 내가 한 신고 같은 다른 기록도 그대로 둘 수 있다 | 댓글을 보여 주는 곳(`005`, `006`)마다 탈퇴 여부를 확인해야 한다. 회원 줄의 개인 정보가 남는다(`D-2`) |
| B. 댓글의 작성자 칸을 비운다 | `comment.users_id`를 비워도 되게 바꾸고, 탈퇴할 때 비운다. 회원 줄은 A처럼 남긴다 | `상세/02`의 현재 가안 그대로. 비어 있으면 "탈퇴한 사용자"라 표시가 단순하다 | **팀 ERD 변경 ⚠**. 댓글 표에 걸린 "회원·글마다 한 개" 규칙(ERD 주석)과도 다시 맞춰야 한다 |
| C. B + 회원 줄을 실제로 지운다 | 탈퇴하면 회원 줄까지 지운다 | 개인 정보가 남지 않는다 | **팀 ERD 변경 ⚠**. `deleted_at`이 쓸모없어지고 `001` D-4를 다시 정해야 한다. 내가 한 신고, 내가 누른 좋아요 등 회원을 가리키는 모든 줄을 먼저 정리해야 한다 |

- **추천**: **A**. ERD를 고치지 않고, 이미 정한 `001` D-4와 그대로 맞는다.
- **A를 고를 때 꼭 지킬 것**: 화면에 작성자를 보여 줄 때 **회원 줄의 닉네임을 그대로 쓰지 말고 탈퇴 여부를 먼저 본다.** 탈퇴한 사람이 같은 닉네임으로 다시 가입하면(FR-028), 옛 줄과 새 줄의 닉네임이 같아서 옛 댓글이 새 계정이 쓴 것처럼 보일 수 있다(SC-008).
- **영향**: A나 B면 `상세/02` `구현 방식`의 "탈퇴 시 데이터" 줄을 고친다(두 곳이 같이 바뀐다). `005`(CF-18-6)와 `006`(댓글 목록)의 plan에서 표시 규칙을 같이 쓴다.

### D-2. 탈퇴한 회원 줄에 남는 개인 정보 — `미정` (`D-1`이 A나 B일 때)

- **문제**: 회원 줄을 남기면 이메일, 닉네임, 소개, 비밀번호 해시가 그대로 남는다. 명세에는 이것을 지우라는 요구가 없지만, "탈퇴했는데 내 정보가 남아 있다"는 것은 사용자가 기대하지 않을 수 있다. 로그인과 중복 검사는 이미 탈퇴하지 않은 회원만 보므로(`001`), 남아 있어도 동작에는 문제가 없다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 그대로 둔다** | 탈퇴 표시만 한다 | 가장 단순하다 | 개인 정보가 남는다 |
| B. 소개만 비운다 | 꼭 필요하지 않은 칸만 지운다 | 거의 단순하다 | 이메일·닉네임은 남는다 |
| C. 이메일·닉네임도 알아볼 수 없는 값으로 바꾼다 | 예: `deleted-123@…` | 개인 정보가 거의 남지 않는다 | 탈퇴 처리가 늘어난다. 이 경우 `001` D-4의 부분 중복 불가가 필요 없어지므로 함께 다시 본다 |

- **추천**: MVP에서는 **A**로 두고, 배포 전에 개인 정보 보관 기준을 정하면서 다시 본다. (헌법 원칙 V: 새 요구는 "추후 확장 후보"로)
- **영향**: B·C면 탈퇴 묶음에 회원 줄 수정이 늘어난다. C면 `001` D-4 결정도 다시 본다.

### D-3. 비밀번호 변경·탈퇴에서 잠겼을 때 보여 줄 문구 — `미정` (FR-018, FR-022)

- **문제**: `상세/02`의 `안내 문구` 표에는 잠금 문구가 없다. `상세/01`의 표에 있는 문구는 "**로그인 시도가** 5회 실패해 잠겼습니다. {N}분 뒤에 다시 시도해 주세요"인데, 비밀번호 변경 화면에서 틀려 잠긴 사람에게는 맞지 않는다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| A. `상세/01`의 문구를 그대로 쓴다 | 로그인과 같은 문구 | 문서를 안 고친다 | 비밀번호 변경·탈퇴에서는 어색하고, 사용자가 이유를 헷갈릴 수 있다 |
| **B. `상세/02` `안내 문구` 표에 새 문구를 더한다** | 예: "비밀번호를 5회 잘못 입력해 잠겼습니다. {N}분 뒤에 다시 시도해 주세요" (문구는 예시) | 상황에 맞다 | 표에 한 줄을 더해야 한다 |

- **추천**: **B**. 문구는 사용자가 정한다. 정하기 전까지 계약은 A의 문구(`상세/01` 표의 문구)를 임시로 쓰고, D-3을 가리켜 둔다.
- **영향**: `상세/02` `안내 문구` 표, contracts 3·4.

### D-4. 현재 비밀번호를 맞게 입력하면 실패 횟수를 0으로 되돌릴까 — `미정` (FR-018, SC-006)

- **문제**: CF-02-7은 "**로그인에 성공하면** 0이 된다"고 하지만, 비밀번호 변경·탈퇴에서 비밀번호를 맞게 넣었을 때는 정해져 있지 않다. FR-018은 "**연속** 5회"라고 한다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 0으로 되돌린다** | 맞게 넣으면 로그인 성공처럼 다시 센다 | "연속"의 뜻에 맞고 로그인과 같다 | — |
| B. 되돌리지 않는다 | 로그인 성공 때만 0 | 로그인 기록만 기준이 된다 | 로그인 3회 실패 → 비밀번호 변경 성공 → 로그인 2회 실패에 잠기는데, 이것은 "연속 5회"가 아니다 |

- **추천**: **A**. 비밀번호 변경 화면에서 현재 비밀번호가 맞은 순간(새 비밀번호 검사 결과와 상관없이) 0으로 한다.
- **영향**: B-2의 4단계, quickstart S-6.

### D-5. 탈퇴 때 신고 기록을 어떻게 할까 — `미정` (FR-024)

- **문제**: 명세는 신고를 말하지 않는다. 그런데 ERD의 `post_report`, `comment_report`는 글·댓글·회원을 가리키므로 탈퇴할 때 어떻게 할지 정해야 한다. 신고 내용은 관리자 화면 없이 DB에서 직접 본다(CF-23-1).
  - **내 글에 대한 신고**: 내 글이 지워지므로 함께 지워야 한다(지우지 않으면 DB가 글 삭제를 거절한다). 내 블로그 글에 달린 댓글에 대한 신고도 같다.
  - **내가 한 신고**: 남길 수도 지울 수도 있다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 내가 한 신고는 남긴다** | 신고당한 글은 그대로 검토할 수 있다 | 신고 기록이 사라지지 않는다. `D-1` A면 회원 줄이 남아 그대로 둘 수 있다 | 탈퇴한 사람의 기록이 남는다 |
| B. 내가 한 신고도 지운다 | 내가 남긴 것은 모두 지운다 | 깔끔하다 | 검토 중인 신고가 사라진다 |

- **추천**: **A** (내 글·내 블로그 댓글에 대한 신고는 글과 함께 지우고, 내가 한 신고는 남긴다).
- **영향**: data-model 3의 순서. `D-1`이 C면 A는 쓸 수 없다(회원 줄이 없으므로).

### D-6. 비밀번호 변경 알림 메일(FR-021, CF-15-16)을 넣을까 — `미정`

- 원본 `정하지 못한 것`에 있는 항목이다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 넣는다 | 비밀번호가 바뀌면 가입 이메일로 알린다 | 본인이 바꾸지 않았을 때 알아챌 수 있다 | SMTP 발송 계정(`001` D-1)이 정해져야 한다. 메일 한도를 쓴다 |
| **B. 이번에는 넣지 않는다** | "추후 확장 후보"로 둔다 | 만들 것이 줄어든다. 비밀번호 변경은 그대로 동작한다 | 알림이 없다 |

- **추천**: **B** (헌법 원칙 V). 
- **A를 고르면 (가안)**: 비밀번호 저장이 끝난 **뒤에** 보내고, 발송이 실패해도 변경은 되돌리지 않는다. 사용자에게 실패를 알릴 필요가 없으므로 `001`의 인증 메일과 달리 맡겨 놓고 보내도(`@Async`) 된다. 메일에 비밀번호를 넣지 않는다.
- **영향**: US4, quickstart S-10.
