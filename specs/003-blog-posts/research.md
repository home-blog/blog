## B. 이 기능에서 고른 기술과 이유 (모두 `가안`)

각 항목은 **Decision / Rationale / Alternatives** 순서입니다.

### B-1. 가입 때 블로그와 `미분류` 만들기 (FR-001 ~ 003, SC-001)

- **쉬운 설명**: 회원이 생기는 순간 블로그와 기본 분류도 **같이** 생겨야 합니다. 셋 중 하나만 생기면 "블로그 없는 회원"이나 "분류 없는 블로그"가 생기므로, 세 개를 한 묶음으로 저장합니다.
- **Decision**: `blog` 모듈이 "기본 블로그 만들기" 입구를 하나 두고, `001`의 가입 처리가 **자기 묶음(트랜잭션) 안에서** 이 입구를 부른다. 블로그 이름 `{닉네임}의 블로그`, 소개 비움, 분류 `미분류`(`is_default` 참, 순서 1, `visibility` = `public`).
- **Rationale**: 묶음은 `001`이 이미 정했다. `003`은 무엇을 만들지만 책임진다.
- **Alternatives**: 처음 내 블로그를 열 때 만들기(첫 방문 전에는 블로그가 없어서 SC-001을 어김). 쓰지 않는다.

### B-2. 권한 검사: 서버가 요청마다, "내 것"은 세션으로 찾는다 (FR-006, 008, 019, 021, 035, 044, SC-004, NF-02)

- **쉬운 설명**: 화면에서 버튼을 숨기는 것은 편의일 뿐입니다. 누군가 화면을 거치지 않고 요청을 보내도, **서버가 "이 사람이 주인인가"를 매번 확인**합니다.
- **Decision**
  1. 블로그 이름·소개와 분류 관리는 주소에 블로그 번호를 받지 않고 `/api/me/blog/...`로 만든다. 서버는 **세션의 회원 번호로 내 블로그를 찾는다.** 그래서 남의 블로그를 고르는 방법 자체가 없다. (US2-10, US6-11, US7-5)
  2. 분류 번호를 받는 요청은 그 분류가 **내 블로그의 것인지** 확인하고, 아니면 없는 분류로 답한다.
  3. 글 수정·삭제·수정 화면 조회는 글 → 분류 → 블로그 → 주인으로 따라가 로그인한 회원과 비교한다. 아니면 **`404` "존재하지 않는 글입니다"**. (FR-019. `001` 계약 9는 권한 없음의 `403`을 기능마다 정하라고 했고, 이 기능은 명세에 따라 `404`로 통일한다)
  4. 글쓰기는 글이 들어갈 블로그를 세션으로 정하고, 고른 분류가 내 블로그의 것이 아니면 거절한다. (FR-008, US2-10)
- **Rationale**: 헌법 원칙 IV, NF-02, 기술스택-아키텍처 3장 D.
- **Alternatives**: `/api/blogs/{blogId}/categories`처럼 블로그 번호를 받고 주인을 비교하기. 가능하지만 비교를 빠뜨리면 바로 구멍이 된다. 읽기 주소(누구나 보는 것)에만 블로그 번호를 쓴다.

### B-3. "보이는 글" 조건을 한곳에 (FR-026, 030, 031, 043, 048, SC-002, SC-003, SC-013)

- **쉬운 설명**: 비공개 글이 **어느 한 화면에서라도** 새면 안 됩니다. 화면마다 따로 조건을 쓰면 하나쯤 빠뜨리기 쉬우므로, "이 사람에게 이 글이 보이는가"를 **한 곳에 한 번만** 적고 모두가 그것을 씁니다.
- **Decision**: 조건은 (`post.visibility = 'public'` **그리고** `category.visibility = 'public'`) **또는** `글의 블로그 주인 = 지금 로그인한 회원`. 글 상세, 분류 목록과 분류별 글 개수, 그리고 `004`의 목록·검색이 이 조건을 쓴다. 이전·다음 글은 명세대로 **공개 글만**(주인이 봐도 공개 분류의 공개 글만) 쓴다. (FR-024, FR-048) 분류 목록은 같은 뜻으로 `category.visibility = 'public'` **또는** 주인일 때만 그 분류를 보여 준다. (2026-10-07: 분류 공개 여부 추가, `D-5`)
- **Rationale**: SC-002를 지키는 가장 단순한 방법.
- **Alternatives**: 화면별로 조건 쓰기. 빠뜨릴 위험이 커서 쓰지 않는다.

### B-4. 입력 검사와 글자 정리 (FR-004, 005, 010, 011, 016, 036)

- **Decision**: 서버에서 Bean Validation으로 검사하고, 검사 **전에** 다음과 같이 정리한다.
  - 블로그 이름, 글 제목, 분류 이름: 앞뒤 공백을 지운다. 지운 뒤 비어 있으면 "비어 있음".
  - 본문: 앞뒤 공백을 **지우지 않는다** (마크다운에서 들여쓰기와 빈 줄이 뜻을 가지기 때문). 줄바꿈 `\r\n`은 `\n`으로 맞춘다. 공백만 있는 본문은 `D-2`.
  - 블로그 소개: 명세에 공백 규칙이 없어서 **앞뒤 공백을 지우고, 지운 뒤 비면 빈 소개로 저장**하는 것으로 해석했다 (`가안`).
- **글자 수 세는 법**: 화면(JavaScript), 서버(Java), DB가 글자 수를 서로 다르게 셀 수 있다. 이모지 같은 글자는 Java의 기본 길이로 2개로 셀 수 있다. 서버는 **사람이 보는 글자 하나를 1자로 세는 방식**(유니코드 코드 포인트)으로 세고, PostgreSQL `VARCHAR(n)`도 글자 단위로 세는 것을 구현 때 확인한다. (구현 때 확인)
- **Rationale**: 헌법 원칙 IV(서버 검증).

### B-5. 이전·다음 글 (FR-024)

- **Decision**: 같은 블로그의 공개 글을 (작성 시각, 글 번호) 순서로 줄 세우고, **이전 글 = 바로 앞에 쓴 글, 다음 글 = 바로 뒤에 쓴 글**로 본다 (`가안`). 작성 시각이 같으면 글 번호로 순서를 정한다. (CF-10-1의 "시각이 같으면 나중에 만든 글이 위"와 같은 기준)
- 각각 한 건만 찾는 쿼리 두 개로 만든다. 없으면 `null`을 주고 화면이 버튼을 숨긴다.
- **주의**: "이전"이 오래된 쪽인지 새 쪽인지 명세에 없다. 화면 시안에 맞추고, 다르면 이 줄만 고친다.

### B-6. 글쓰기 기본 분류와 기본 주제 (FR-012, FR-046)

- **Decision**: 내 블로그에서 **작성 시각이 가장 늦은 글**의 분류와 주제를 기본값으로 준다. 글이 없으면 분류는 `is_default`가 참인 분류(`미분류`)이고, 주제는 **비워 둔다**(사용자가 골라야 저장된다). 수정한 글은 따지지 않는다 ("마지막에 쓴 글"을 작성 기준으로 해석, `가안`).
- **Alternatives**: 마지막으로 고른 분류를 회원별로 따로 저장. 칸이 늘어서 쓰지 않는다.

### B-7. 수정 시각은 "바뀌었을 때만" (FR-020, SC-009)

- **Decision**: 서버가 요청의 제목·본문·분류·주제·공개 여부를 **지금 값과 하나씩 비교**하고, 하나라도 다르면 바꾼 값과 함께 `updated_at = 지금`을 저장한다. 모두 같으면 아무것도 저장하지 않고 성공으로 답한다. `created_at`은 수정 요청에서 바꿀 수 없게 한다.
- 비교는 B-4의 **정리를 마친 값**으로 한다. (제목 앞뒤 공백만 달라진 것은 "바뀌지 않음")
- **위험**: [R-2](#r-2-수정-시각을-프레임워크가-자동으로-바꿀-수-있다)

### B-8. 글 삭제는 한 묶음 (FR-022, SC-007)

- **쉬운 설명**: 글을 지우는데 댓글만 남거나, 댓글은 지웠는데 글이 남으면 안 됩니다. **모두 지우거나, 하나도 안 지우거나** 둘 중 하나여야 합니다.
- **Decision**: 서비스가 하나의 묶음(트랜잭션) 안에서 다음 순서로 지운다: 댓글의 신고(`D-7`) → 댓글 → 좋아요 → 태그 연결 → 이미지 기록 → 글의 신고(`D-7`) → 글. 이미지 **파일**은 묶음이 성공한 뒤에 지운다 ([R-1](#r-1-이미지-파일은-묶음-밖에-있다)).
  - 대댓글은 같은 `comment` 표 안에서 서로를 가리키므로, 한 번에 지울 때 DB가 순서를 문제 삼지 않는지 구현 때 확인한다. (구현 때 확인)
  - 댓글·좋아요·태그·이미지 표는 `005`의 모듈이 다루므로, `post` 모듈은 그 모듈이 제공하는 "이 글의 것 모두 지우기" 입구를 부른다.
- **Rationale**: 팀 ERD의 외래 키에 **연쇄 삭제(`ON DELETE CASCADE`)가 없다.** 서비스에서 순서대로 지우면 ERD를 바꾸지 않아도 된다.
- **Alternatives**: 외래 키에 연쇄 삭제를 건다. 코드는 줄지만 ERD 변경이 필요하고, 무엇이 지워지는지 코드에서 보이지 않는다.

### B-9. 바로 반영 (FR-006, 038, SC-010)

- **Decision**: 블로그 이름, 소개, 분류 이름을 **캐시하지 않고** 요청마다 DB에서 읽는다. 글은 분류 번호만 가지고, 상세 화면은 블로그 이름·분류 이름을 그때그때 읽는다.
- **Rationale**: 규모가 작아 캐시가 필요 없고, 캐시가 없으면 옛 값이 보일 일도 없다.
- **나중에 캐시를 두면**: 저장할 때 그 캐시를 지우는 일이 같이 필요하다. (추후 확장 후보)

### B-10. 스크립트와 SQL 안전 (FR-045, SC-012, NF-07)

- **SQL**: 모든 조회는 JPA 또는 파라미터를 따로 넘기는 쿼리로 만든다. 문자열을 이어 붙이지 않는다. (상세/07, 헌법 원칙 IV)
- **스크립트**: 제목, 블로그 이름, 소개, 분류 이름은 **글자 그대로** 보여 준다 (React의 기본 이스케이프, 상세/07). 본문은 마크다운이라 이것만으로는 부족하다 → **`D-1`**.
- **서버 쪽 보조 장치 (가안)**: 응답에 브라우저가 스크립트 실행을 제한하도록 하는 보안 헤더(Content-Security-Policy)를 거는 것을 검토한다. 이미지 주소(`005`)와 함께 정해야 하므로 `tasks`에서 다시 본다.

## C. 위험과 확인할 점

### R-1. 이미지 파일은 묶음 밖에 있다

- **무슨 문제인가**: DB의 이미지 기록은 글과 한 묶음으로 지울 수 있지만, **파일**은 DB 밖(서버 디스크 또는 MinIO, 저장 위치 `미정`)에 있어서 같은 묶음에 넣을 수 없다. 파일 삭제가 실패하면 **주인 없는 파일**이 남는다. SC-007의 "이미지가 남아 있는 경우 0건"을 어떻게 셀지에 따라 문제가 된다.
- **대안 (가안)**: DB 묶음이 성공한 뒤 파일을 지우고, 실패하면 기록해 두었다가 `@Scheduled`로 다시 지운다. 저장소 구조는 `005`의 plan에서 정한다.
- **상태**: 위험으로 기록. `005`와 함께 확인.

### R-2. 수정 시각을 프레임워크가 자동으로 바꿀 수 있다

- JPA의 "수정 시각 자동 기록" 기능을 쓰면 **내용이 같아도 저장 요청만으로 시각이 바뀔 수 있는지** 확실하지 않다. (구현 때 확인) 그래서 B-7처럼 서비스가 직접 비교하고 직접 시각을 넣는 방식을 쓴다. 확인 시나리오는 [quickstart.md](quickstart.md) S-7.

### R-3. 분류를 지우는 순간 글이 들어오는 경우 (FR-040, SC-005)

- 서버가 "글 0개"를 확인한 직후 다른 요청이 그 분류에 글을 넣을 수 있다. 팀 ERD의 `post.category_id → category` 외래 키에는 연쇄 삭제가 없으므로 **DB가 삭제를 거절한다** (마지막 방어선). 이때는 `CATEGORY_HAS_POSTS`로 다시 세어 답한다.
- `상세/03`의 "글이 있는 분류는 DB에서도 막는 안"은 이 외래 키로 이미 지켜진다.

### R-4. 블로그 주인이 1명뿐인 구조에 기대고 있다

- 글 표에 작성자 칸이 없고, 작성자 = 블로그 주인이다 (명세 Key Entities). 나중에 공동 블로그를 만들면 권한 검사 전체를 다시 봐야 한다. `D-4`와 함께 기록만 한다.

### R-5. 두 화면에서 같은 글을 동시에 고치는 경우

- 명세에 없다. 지금은 **나중에 저장한 쪽이 이긴다.** 막아야 하면 명세부터 정한다. (헌법 원칙 V, 기록만)

### R-6. 비공개 글이 "다른 길"로 드러날 수 있다 (SC-002, SC-003)

- 응답 문구만 같아도 아래가 다르면 비공개 글이 있다는 것이 드러난다. 모두 같게 만든다.
  - 상태 코드와 응답 본문 (없는 글과 똑같이 `404`, 같은 `code`, 같은 `message`)
  - 수정 화면 조회·수정·삭제 요청에서도 남의 글이면 같은 `404` (FR-019)
  - 이전·다음 글 번호에 비공개 글을 넣지 않는다 (B-5)
  - 방문자의 분류별 글 개수에 비공개 글과 비공개 분류의 글을 넣지 않는다 (FR-043)
  - 비공개 분류의 글은 주소로 열어도 없는 글과 같은 `404`, 비공개 분류는 방문자의 분류 목록에 넣지 않는다 (FR-048)
  - 응답 시간 차이는 이 규모에서 따로 맞추지 않는다 (기록만)
- 반대로, **분류 삭제 거절 문구의 `{N}`** 은 주인만 보는 숫자이므로 비공개 글을 포함한다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 마크다운을 그리되, HTML은 글자로 보이게** | 마크다운 문법(굵게, 목록, 링크, 이미지)만 그린다. 본문에 쓴 `<script>`, `<img onerror>` 같은 HTML은 **그리지 않고 글자 그대로** 보여 준다. `javascript:` 같은 위험한 링크 주소는 막는다 | 확정된 편집기를 지킨다. - **영향**

### D-2. 본문 글자 수를 어떻게 세고, 공백만 있는 본문을 어떻게 볼까 — `미정` (FR-011, FR-016)

### D-3. 팀 ERD의 `post.topic_id`(필수)를 어떻게 할까 — **결정됨 (2026-10-07)** (FR-009, FR-020, FR-046, SC-013)

> **결정 (2026-10-07)**: **C.** 글쓰기에 주제 입력을 더한다. 팀 ERD의 `post.topic_id`(NOT NULL, `topic` 외래 키)는 **그대로** 쓴다. 주제는 필수이고, 기본값은 마지막에 쓴 글의 주제, 처음에는 비어 있어서 골라야 한다("주제를 골라 주세요").
> **2026-10-07 사용자 결정으로 A에서 C로 바꿈.** 명세는 FR-009, FR-020(입력·수정 항목에 주제), FR-046(주제 규칙)으로 고쳤고, `상세/03`에 CF-05-16을 더했다. `요구사항.md`의 `용어`와 헌법의 `용어`(1.2.0)도 주제를 **글마다 고르는 분류**로 바꿨다. 그래서 팀 ERD 변경 요청(`post.topic_id` 삭제, `blog.topic_id` 추가)은 **하지 않는다.**

- **문제였던 것** (결정 전): 팀 ERD의 `post`에는 `topic_id BIGINT NOT NULL`과 `topic` 표로의 외래 키가 있다. 그런데
  - 그때 명세는 글쓰기 입력을 **제목, 본문, 분류, 공개 여부**로 정했고, 주제는 다루지 않았다.
  - 그때 `요구사항.md`와 헌법의 `용어`는 주제를 **블로그 전체를 묶는 분류**라고 했다. (지금은 둘 다 "글마다"로 고쳤다)
  - 이대로면 **글을 저장할 수 없었다** (필수 칸을 채울 값이 없다).

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| A. 주제를 블로그로 옮긴다 | `post.topic_id`를 없애고 `blog.topic_id`를 둔다 (처음에는 비워 둘 수 있게) | 그때의 용어 정의와 맞았다. 글쓰기 입력이 그때 명세와 같았다 | 팀 ERD 변경. 블로그 주제를 누가 언제 고르는지 정해야 한다 (`002` 또는 `004`) |
| B. `post.topic_id`를 비워 둘 수 있게 | 칸은 두고 `NULL`을 허용한다 | 변경이 가장 작다 | 주제가 글마다인지 블로그마다인지 계속 헷갈린다 |
| **C. 글쓰기에 주제 입력을 더한다** (결정) | 글마다 주제를 고른다 | **ERD 그대로.** 팀 ERD의 뜻과 같다 | 명세와 용어 정의를 바꿔야 한다 → 2026-10-07에 바꿨다 |

- **처음 추천**: A였다. 사용자가 팀 ERD의 뜻(글마다 주제)을 따르기로 해서 C로 정했다.
- **영향**
  - 글쓰기·수정 요청에 `topicId`가 생긴다 (contracts 9, 10, 12, 13). 서버는 그 번호가 `topic` 표에 **있는지** 확인한다.
  - 기본 주제는 B-6의 기본 분류와 같은 방식으로 정한다: 내 블로그에서 작성 시각이 가장 늦은 글의 주제. 글이 없으면 비워 둔다.
  - 주제 목록(여행, 음식, 취미, 운동, 개발)은 팀 ERD의 `topic` 표에서 읽는다. 이 기능은 목록을 바꾸지 않는다.
  - 주제별 화면은 `요구사항.md`의 개인 기능이라 이 기능에서 다루지 않는다.

### D-4. 회원–블로그를 1:1로 둘까, 1:N으로 둘까 — **결정됨 (2026-10-07)** (FR-001, SC-001)

> **결정 (2026-10-07)**: **A.** 1:1. 팀 ERD의 `blog.users_id` `UNIQUE`를 그대로 쓴다. `상세/03`의 "1:N 구조" 문구를 1:1로 고쳤다.

- **문제**: `상세/03` `구현 방식`은 "회원–블로그는 **1:N 구조**로 만들고 서버에서 1개까지로 제한"이라고 적었다. 팀 ERD는 `blog.users_id`에 **`UNIQUE`**(1:1)를 걸었다. 그리고 원본의 "정하지 못한 것"에 **"블로그를 여러 개 만들 수 있게 할지"** 가 그대로 남아 있다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. ERD 그대로 1:1 (`UNIQUE`)** | DB가 "회원 1명당 블로그 1개"를 직접 지킨다 | 서버 실수가 있어도 블로그 2개가 생기지 않는다 (SC-001) | 여러 블로그로 늘릴 때 `UNIQUE`를 지우는 변경이 필요하다 (작은 변경) |
| B. 1:N + 서버에서 1개 제한 (`상세/03` 가안) | DB는 여러 개를 허용하고 서버 코드가 막는다 | 나중에 늘리기 쉽다 | 서버가 빠뜨리면 2개가 생길 수 있다. 팀 ERD의 `UNIQUE`를 지워 달라고 해야 한다 |

- **추천**: **A**. 지금 범위는 1인 1블로그이고, 늘릴 때 `UNIQUE` 하나만 지우면 된다.
- **영향**: A를 고르면 `상세/03`의 "1:N 구조" 줄을 "1:1(`UNIQUE`), 확장할 때 1:N"으로 고쳐야 한다. "블로그를 여러 개 만들 수 있게 할지"는 **원본의 미정 그대로** 둔다.

### D-5. 분류 표를 어떻게 맞출까 (순서, 대소문자, `visibility`, `intro`) — **결정됨 (2026-10-07)** (FR-028, FR-036, FR-037, FR-039, FR-047, FR-048, SC-006, SC-013)

  4. `intro`(분류 소개) 칸은 명세에 없다. (쓰지 않으면 문제는 없다)

|---|---|---|---|
| **A. 소문자로 바꾼 값에 중복 불가를 건다** | PostgreSQL의 식 인덱스 `UNIQUE (blog_id, lower(name))` | 칸을 늘리지 않는다. `001`의 `D-4`(소문자 비교)와 같은 방식 | MySQL로 바꾸면 방법이 달라진다 |
| B. 비교용 칸을 하나 더 둔다 | `name_key`에 소문자로 바꾼 값을 저장하고 `UNIQUE(blog_id, name_key)` | 어떤 DB에서나 된다 | 칸이 늘고, 두 칸을 항상 같이 바꿔야 한다 |
| C. 서버에서만 검사한다 | ERD의 `UNIQUE` 그대로 | ERD 변경이 없다 | 거의 동시에 두 요청이 오면 `Daily`와 `daily`가 둘 다 생길 수 있다 (SC-006 위반) |

- **(3) `category.visibility`** (2026-10-07 결정): **쓴다.** 값은 `public` / `private`, 기본 `public`.
  - 다른 사람(로그인하지 않은 사람 포함)에게 글이 보이는 조건은 `post.visibility = 'public'` **그리고** `category.visibility = 'public'`이다. 블로그 주인은 모두 본다. (B-3, FR-048)
  - 비공개 분류의 글은 공개 글이어도 **비공개 글과 똑같이** 다룬다: 목록, 검색, 이전/다음 글에서 빠지고, 주소로 열면 "존재하지 않는 글입니다". (FR-031, FR-048, R-6)
  - 비공개 분류는 다른 사람의 분류 목록에도 나오지 않는다. (FR-048)
  - 처음 추천은 "삭제 요청"이었다. 사용자가 팀 ERD의 뜻을 살리기로 해서 바꿨다.
- **결정 요약**: `sort_order` 그대로 + **(2) A** + `visibility` 사용 + `intro`는 쓰지 않음.
- **영향**: 팀 ERD 변경 요청은 (2) 1건과 `CHECK (visibility IN ('public','private'))` 제안뿐이다. `001`의 가입 묶음이 `미분류`를 만들 때 `sort_order = 1`, `visibility = 'public'`을 넣으므로 **`001`의 data-model 2번 표도 함께 고친다.** `006`의 분류 관리 화면(BM-04)도 같은 순서 칸을 쓰고, 공개/비공개 바꾸기(`006` FR-042)를 더한다. `004`의 목록·검색도 같은 조건을 쓴다 (`004` D-7).

### D-6. 연속 저장을 서버에서 한 번만 처리하는 방법 — **결정됨 (2026-10-07)** (FR-018, SC-008)

> **결정 (2026-10-07)**: **A.** 글쓰기 화면을 열 때 화면이 1회용 요청 번호를 만들어 저장 요청에 싣고, 서버는 `post.request_key`(비워 둘 수 있음, 중복 불가)에 저장한다. 같은 번호가 다시 오면 처음 만든 글 번호를 돌려준다. 화면 버튼 잠금도 함께 한다. **팀 ERD에 칸 추가를 요청**한다.

- **문제**: 글에는 이메일처럼 "겹칠 수 없는 값"이 없어서, `001`의 가입처럼 DB 중복 불가로 막을 수 없다. 화면의 버튼 잠금만으로는 느린 네트워크에서의 재전송, 두 번 빠르게 누르기의 틈을 다 막지 못해 SC-008(0건)을 장담할 수 없다.
- **Redis는 쓰지 않는다**: "이 요청은 이미 처리했다"를 Redis에 잠깐 두는 방법이 흔하지만, 헌법이 Redis를 **이메일 인증번호 저장에만** 쓰게 했으므로 선택지에서 뺐다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 1회용 요청 번호를 글에 저장** | 글쓰기 화면을 열 때 화면이 무작위 번호를 만들고 저장 요청에 싣는다. 서버는 `post`에 이 번호를 저장하고 **중복 불가**를 건다. 같은 번호가 다시 오면 처음 만든 글 번호를 돌려준다 | DB가 마지막 방어선이 되어 SC-008을 확실히 지킨다 | ⚠ 팀 ERD에 칸 하나(`post.request_key`, 비워 둘 수 있음) 추가 요청 |
| B. 화면 버튼 잠금만 | 저장을 누르면 응답이 올 때까지 버튼을 누를 수 없게 한다 | 가장 단순하다. ERD 변경 없음 | 화면을 거치지 않는 재전송은 막지 못한다 |
| C. 짧은 시간 안의 같은 내용을 막는다 | 같은 블로그에 같은 제목·본문의 글이 몇 초 안에 또 오면 거절한다 | ERD 변경 없음 | 시간 기준이 애매하고, 일부러 같은 글을 두 번 쓰는 경우와 구분하기 어렵다 |

- **추천**: **A** (화면 버튼 잠금도 함께).
- **영향**: 팀 ERD 변경 요청. 계약의 글쓰기 요청에 `requestKey`가 생긴다 (contracts 10).

### D-7. 글을 지울 때 그 글과 댓글의 신고 기록을 어떻게 할까 — **결정됨 (2026-10-07)** (FR-022, SC-007)

> **결정 (2026-10-07)**: **A.** 글을 지우면 그 글과 그 글 댓글의 신고 기록도 함께 지운다. (`005` D-11과 같음) 신고 처리 기능을 만들 때 다시 검토한다.

- **문제**: 명세 FR-022는 글과 함께 지울 것을 **댓글, 좋아요, 태그 연결, 이미지**로 적었다. 그런데 팀 ERD의 `post_report`(글 신고)와 `comment_report`(댓글 신고)도 글·댓글을 외래 키로 가리킨다. 아무것도 정하지 않으면 **신고가 달린 글은 지울 수 없다** (DB가 거절). 신고 내용은 관리자 화면 없이 DB에서 직접 확인한다(CF-23-1).

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 신고 기록도 함께 지운다** | 글을 지우면 그 글과 그 글 댓글의 신고도 지운다 | 가장 단순하다. ERD 변경 없음 | 신고된 글을 작성자가 지우면 신고 기록이 사라진다 |
| B. 신고 기록은 남긴다 | 신고 표의 글 번호를 비워 둘 수 있게 하고, 글을 지우면 번호만 비운다 (필요하면 제목 사본을 남김) | 신고 기록이 남는다 | ⚠ 팀 ERD 변경. 무엇을 남길지 더 정해야 한다 |
| C. 신고가 있는 글은 지우지 못하게 | 신고가 있으면 삭제를 거절한다 | 기록이 확실히 남는다 | **명세 FR-021(작성자는 지울 수 있다)과 어긋난다** |

- **추천**: **A** (MVP). 신고 처리 기능(CF-23)을 만들 때 B를 다시 검토한다 (추후 확장 후보).
- **영향**: `005`의 신고 plan과 맞춘다. 명세의 FR-022 목록에 신고를 더할지는 사용자 확인 뒤 명세에서 정한다.
