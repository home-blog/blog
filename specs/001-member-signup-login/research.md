## B. 이 기능에서 고른 기술과 이유 (모두 `가안`)

각 항목은 **Decision / Rationale / Alternatives** 순서입니다.

### B-1. 비밀번호 저장: BCrypt 해시 (FR-010, NF-01)

- **쉬운 설명**: 비밀번호를 **되돌릴 수 없는 다른 값**으로 바꿔서 저장합니다. 같은 비밀번호도 저장되는 값이 매번 달라서, 저장된 값이 새어도 원래 비밀번호를 알아내기 어렵습니다.
- **Decision**: BCrypt (강도 10~12). 상태 `가안`.
- **Rationale**: Spring Security가 기본으로 제공해서 직접 만들 코드가 없다. 허용 글자가 모두 1바이트라 20자는 BCrypt의 72바이트 한도 안이다.
- **Alternatives**: Argon2(더 새롭지만 설정이 늘어남), 일반 SHA-256(너무 빨라서 비밀번호에는 부적합). 쓰지 않는다.

### B-2. 입력 검사는 서버가 마지막 방어선 (FR-001~009, FR-034)

- **쉬운 설명**: 화면의 검사는 편의일 뿐이고, 화면을 거치지 않고 서버에 직접 요청해도 **서버가 같은 규칙으로 막습니다.**
- **Decision**: 서버에서 Bean Validation과 정규식으로 검사하고, 화면도 같은 규칙으로 안내한다. 비밀번호 정규식은 `상세/01`의 `구현 방식`에 적힌 `^(?=.*[A-Za-z])(?=.*\d)(?=.*[!@#$%^&*()_+\-=])[A-Za-z\d!@#$%^&*()_+\-=]{8,20}$`를 쓴다. 비밀번호 확인 일치도 서버가 검사한다. 상태 `가안`.
- **Rationale**: 헌법 원칙 IV(서버 검증), 상세/07 `서버 입력 검사`.
- **Alternatives**: 화면 검사만(우회 가능해서 안 됨).

### B-3. 이메일·닉네임 비교 방식 (FR-003, FR-005, SC-002)

- **쉬운 설명**: `Abc@x.com`과 `abc@x.com`은 같은 이메일이어야 하고, 닉네임 `Kim`과 `kim`도 같은 것으로 봐야 합니다. 비교할 때 **같은 모양으로 맞춘 뒤** 비교합니다.
- **Decision**: 이메일은 앞뒤 공백을 지우고 소문자로 바꿔 저장·비교한다. 닉네임은 **보여 주는 값은 입력한 그대로** 두고, 중복 비교용으로 소문자로 바꾼 값을 따로 쓴다. 상태 `가안`.
- **주의 (팀 ERD)**: 지금 ERD의 `users.nickname`은 `UNIQUE`이지만 **대소문자를 구분하는 비교**다. 소문자 비교 칸을 두거나 소문자로 비교하는 중복 불가 규칙이 필요하다. → **결정 D-4**
- **Alternatives**: DB에서 대소문자 무시 비교 확장(`citext`) 사용. 설치가 하나 늘어서 지금은 쓰지 않는다.

### B-4. 인증번호 생성과 저장: Redis (FR-013~019, NF-05)

- **쉬운 설명**: Redis는 **"10분 뒤에 지워 줘"** 하고 시간을 걸어 둘 수 있는 포스트잇입니다. 인증번호가 10분 뒤 저절로 사라지고, 맞게 입력하면 바로 지워서 다시 쓸 수 없게 하기에 알맞습니다.
- **Decision**: `SecureRandom`으로 6자리(영문 대문자+숫자, `O`·`0`·`I`·`1` 제외)를 만들고, 이메일을 이름표로 Redis에 저장한다. 키 목록은 [data-model.md](data-model.md)에 있다. 상태: 인증번호 저장 `확정`, 나머지 키 설계 `가안`.
- **Rationale**: 만료와 1회용을 자동으로 지킨다. (FR-016, FR-017)
- **Alternatives**: PostgreSQL에 저장하고 만료된 것을 지우는 작업을 따로 만든다. 가능하지만 정리 작업이 늘어난다.
- **Redis 사용 범위**: 아래 [결정 D-6](#d-6-redis를-어디까지-쓸까-헌법-해석)을 본다.

### B-5. 세션: 서버가 명부를 들고 있는 방식 (FR-030~032, NF-10, NF-12)

- **Decision**: Spring Security + Spring Session JDBC. 쿠키는 `HttpOnly`, `SameSite=Lax`, 배포 시 `Secure`. 로그인할 때마다 세션 ID를 새로 발급한다(Spring Security 기본 동작). 마지막 사용 후 7일, 로그인한 때부터 최대 30일. 상태: 방식 `확정`, 속성과 최대 30일 `가안`.
- **Rationale**: 로그아웃하면 바로 끊기고(FR-031) 추가 설치가 필요 없다. (자세한 비교는 상세/01 `쉬운 설명`)
- **Alternatives**: Redis 세션(서버 설정 한 곳만 바꾸면 되지만, Redis가 꺼지면 로그인이 안 됨), JWT(안 씀).
- **위험 R-1 (검증 필요)**: [아래 R-1](#r-1-로그인-유지-7일-연장이-브라우저에서-지켜지는가)을 본다.
- **위험 R-2**: "로그인한 때부터 최대 30일"은 프레임워크의 기본 기능으로 보이지 않는다. (구현 때 확인) 없다면 요청마다 세션을 만든 시각을 확인해서 30일이 지났으면 세션을 지우는 **작은 검사 장치**가 필요하다. (FR-030)

### B-6. 로그인 요청 방식 (FR-024~026, FR-032)

- **Decision**: 화면은 React이므로 로그인을 **JSON 요청**으로 받는 API를 쓴다. Spring Security의 인증 흐름을 쓰고, 실패 원인(없는 이메일, 틀린 비밀번호)은 **같은 응답**으로 합친다. 상태 `가안`.
- **Rationale**: FR-026, FR-035. 응답 시간 차이로 계정 존재를 짐작하지 못하게, 없는 이메일에도 해시 비교를 한 번 돌리는 것을 구현 때 검토한다.

### B-7. CSRF 방어 (NF-11)

- **쉬운 설명**: 다른 사이트가 내 브라우저의 쿠키를 이용해 몰래 요청을 보내는 것을 막는 장치입니다.
- **Decision**: Spring Security의 CSRF 토큰을 쓰고, React가 모든 변경 요청(POST 등)의 헤더에 토큰을 싣는다. 처음 방문한 사람도 가입 요청을 보내야 하므로 **토큰을 먼저 받는 요청**(`GET /api/auth/csrf`)을 둔다. 상태 `가안`.
- **Alternatives**: `SameSite`만 믿기(보조 장치일 뿐이라 부족), CSRF 끄기(안 됨, 쿠키 방식이라 필요).

### B-8. 설정값은 한곳에서 (헌법 원칙 VI, NF-08)

- **Decision**: `application.yml` 한곳에서 읽는다. 값 목록은 [plan.md](plan.md)의 `설정값 목록`에 있다. 상태 `가안`.
- **Rationale**: 숫자를 바꿀 때 코드와 문서가 어긋나지 않게 하고, 테스트 때는 시간을 짧게 줄여 쓸 수 있다. (quickstart.md)

### B-9. 개발 중 메일 (FR-013)

- **Decision**: 개발 환경에서는 실제 메일 대신 **서버 로그에 인증번호를 출력**한다. 이 로그는 개발용 설정에서만 켜고, 배포 설정에서는 끈다. 상태 `가안`. (상세/01)
- **주의**: 인증번호를 로그에 남기는 것은 비밀번호 원문을 로그에 남기지 않는다는 FR-010과 **다른 이야기**다. 그래도 배포에서는 끈다.

## C. 위험과 확인할 점

### R-1. 로그인 유지 "7일 연장"이 브라우저에서 지켜지는가

- **무슨 문제인가**: 서버의 세션은 쓸 때마다 만료가 늘어나지만, **브라우저의 쿠키는 처음 만들 때 정한 만료 시각 그대로**일 수 있다. 그러면 "계속 쓰면 기간이 연장된다"(FR-030)가 서버에서는 지켜져도, 로그인한 지 7일이 지난 날 브라우저가 쿠키를 버려서 로그인이 풀릴 수 있다.
- **확인 방법**: 구현 때 [quickstart.md](quickstart.md)의 시나리오 S-6에서 쿠키 만료 시각이 연장되는지 직접 본다. (이 문서에서는 동작을 단정하지 않는다.)
- **연장이 안 되면 대안**: 요청이 올 때 쿠키를 다시 내려 주는 장치를 더한다.
- **상태**: 위험으로 기록. 결정할 것은 없다.

### R-2. 메일 발송 실패를 사용자에게 알려야 한다 (FR-020)

[결정 D-2](#d-2-인증-메일을-기다렸다-보낼까-맡겨-놓고-보낼까)를 본다.

### R-3. 같은 사람이 동시에 두 번 누르는 경우 (FR-012, FR-023)

- **Decision (가안)**: 화면은 누른 뒤 버튼을 잠근다(보조). 서버는 **이메일의 중복 불가 제약**을 마지막 방어선으로 두고, 가입이 성공하면 "인증됨" 표시를 지운다. 두 요청이 거의 동시에 와도 한 건만 성공하고 나머지는 "이미 가입된 이메일입니다"로 거절된다.
- **Alternatives**: 이메일별 잠금(락)을 거는 방법. 지금 규모에서는 과하다.

### R-4. 잠금 응답이 계정 존재를 드러낸다 (FR-026, FR-027)

- 가입되지 않은 이메일은 잠금 문구가 아니라 일반 실패 문구만 보이므로(CF-02-9), 잠금 문구가 보이면 그 계정이 있다는 뜻이 된다. 이것은 **명세가 정한 절충**이다. (남은 시간을 안내해야 하므로) 바꿀 일이 생기면 명세부터 고친다.

### R-5. 이메일 존재 여부가 드러난다 (FR-004)

- "이미 가입된 이메일입니다"를 보여 주는 것이 요구사항(CF-14-1)이다. 로그인(FR-026)과 달리 **일부러 알려 주는 것**이다.
- 이 응답으로 누군가 이메일이 가입됐는지 하나씩 알아낼 수 있다. 가입된 이메일에는 메일을 보내지 않으므로 FR-018의 횟수 제한에도 걸리지 않는다.
- 막으려면 요청한 곳(IP) 기준의 제한이 필요하다. 명세에 없는 요구라서 이 `plan`에서는 정하지 않고, `tasks` 이후에 넣을지 검토할 항목으로 남긴다. (헌법 원칙 V: 새 아이디어는 MVP에 바로 넣지 않는다)

### D-1. SMTP 발송 계정 — `미정`

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. Gmail** | 구글 계정의 `앱 비밀번호`로 보낸다 | 설정 자료가 많다 | 2단계 인증을 켜야 하고, 하루 발송 한도가 있다 |
| **B. 네이버** | 네이버 메일 설정에서 SMTP 사용을 켠다 | 한국 사용자에게 익숙하다 | 설정 위치가 바뀌기 쉽고, 하루 발송 한도가 있다 |
| **C. 개발 중에는 로그 출력만** | 실제로 보내지 않고 서버 로그에 번호를 찍는다 | 한도 걱정이 없다 | 배포 전에는 A 또는 B가 필요하다 |

- **추천**: **개발 중에는 C를 쓰고**, 실제 발송이 필요해지는 시점에 **지금 쓰는 계정이 있는 쪽(A 또는 B)** 을 고른다. (기술스택-아키텍처 5장의 "사용 계정에 맞춰 선택"과 같은 뜻)
- **비밀번호나 앱 비밀번호는 문서와 저장소에 적지 않는다.** 환경 변수로 넣는다. (공개 저장소이기 때문)

### D-2. 인증 메일을 기다렸다 보낼까, 맡겨 놓고 보낼까 — **결정됨: A (기다렸다 보낸다)**

> **결정 (2026-10-07)**: **A. 기다렸다 보낸다.** 반영한 곳: `상세/01`의 `메일 발송 방식` 줄, `기술스택-아키텍처.md` 2.7, 2.8, 그림 C.

- **문제**: `상세/01`은 메일을 `@Async`(맡겨 놓고 다음 일을 함)로 보내고 **실패하면 안내 문구를 보여 준다**고 적었다. 그런데 맡겨 놓고 보내면 요청에 대한 응답은 이미 "성공"으로 나간 뒤라서, **발송이 실패해도 사용자에게 바로 알릴 방법이 없다.** FR-020("메일 발송에 실패하면 안내 문구를 보여 준다")과 부딪힌다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 기다렸다 보낸다 (동기)** | 메일이 나갈 때까지 응답을 기다린다 | 실패를 바로 알려 줄 수 있다. 가장 단순하다 | 응답이 몇 초 걸릴 수 있다 |
| B. 맡겨 놓고 보내고 상태를 묻는다 | 먼저 "접수됨"을 응답하고, 화면이 결과를 다시 물어본다 | 응답이 빠르다 | 만들 것이 늘어난다 |
| C. 맡겨 놓고 보내고 실패는 알리지 않는다 | `상세/01`의 현재 가안 그대로 | 가장 빠르다 | **FR-020을 지키지 못한다** |

- **추천**: **A (동기)**. 가입 한 번에 메일 한 통이고, 요구사항(FR-020)을 가장 단순하게 지킨다. `@Async`는 다른 곳(통계 집계 등)에서 그대로 쓴다.
- **영향**: `상세/01`의 "비동기 발송" 줄을 "메일 발송 방식"으로 고쳤다. (규칙: 두 곳이 같이 바뀐다 — 반영 완료)
- **발송이 실패했을 때의 처리 (가안)**: 저장한 인증번호를 지우고, 1분·하루 횟수에도 **넣지 않는다.** 그래야 "다시 받기를 누를 수 있다"(FR-020)가 지켜진다.

### D-3. 로그인 실패 횟수와 잠금 시각을 어디에 둘까 — **결정됨: A (회원 표에 칸 추가)**, 팀 ERD 반영 대기

> **결정 (2026-10-07)**: **A.** `users`에 `failed_login_count`, `locked_until`을 둔다. 팀 공통 ERD는 합의 없이 고치지 않으므로 **팀에 칸 추가를 요청**해야 한다. 팀이 받아들이지 않으면 B(Redis)로 바꾸고, D-6의 해석을 넓히는 헌법 확인이 필요하다.

- **문제**: 지금 팀 ERD의 `users` 표에는 **연속 실패 횟수와 잠금 해제 시각 칸이 없다.** FR-027, FR-028을 지키려면 어딘가에 저장해야 한다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. `users`에 칸 두 개를 더한다** | `failed_login_count`, `locked_until` | 단순하고, 서버를 껐다 켜도 남는다. `상세/01`의 현재 가안 | **ERD를 고쳐야 한다** (팀 공통 표) |
| B. Redis에 시간을 걸어 둔다 | 잠금이 시간이 지나면 저절로 풀린다 | ERD를 안 고쳐도 된다. 풀리는 작업이 필요 없다 | 서버/Redis가 꺼지면 잠금이 사라질 수 있고, 헌법의 Redis 범위(원칙 V/`기술 제약`)를 넓혀야 한다 |

- **추천**: **A**. 단순하고 잠금 기록이 남는다. 헌법의 Redis 범위도 지킨다.
- **영향**: A는 팀 ERD(`users`)에 칸 추가가 필요하다. 팀과 합의가 필요한 변경이다. (`요구사항-공통.md`와 ERD는 합의 없이 고치지 않는다 — 헌법 `작업 흐름`)

### D-4. 이메일·닉네임 중복 불가를 어떻게 걸까 — **결정됨: A (탈퇴하지 않은 회원에게만 + 소문자 비교)**, 팀 ERD 반영 대기

> **결정 (2026-10-07)**: **A.** `deleted_at`이 비어 있는 회원에게만 중복 불가를 걸고, 이메일과 닉네임은 소문자로 맞춘 값으로 비교한다. 팀 ERD의 `users`(`email`, `nickname`의 `UNIQUE`)를 이에 맞게 고쳐야 하므로 **팀에 요청**한다. `002`(CF-15-21 재가입)도 같은 결정을 쓴다.

- **문제 1 (대소문자)**: B-3에서 말한 대로, ERD의 `UNIQUE`는 대소문자를 구분한다. FR-003, FR-005는 구분하지 않는다.
- **문제 2 (탈퇴 후 재가입)**: ERD의 `users`에는 `deleted_at`(탈퇴 표시)이 있고 `email`, `nickname`이 `UNIQUE`다. 그런데 `002` 명세는 **탈퇴한 사람이 같은 이메일과 닉네임으로 다시 가입할 수 있다**고 한다. 탈퇴한 줄이 남아 있으면 중복 불가 규칙에 걸려서 재가입이 막힌다. 그리고 FR-004("이미 가입된 이메일")는 **탈퇴하지 않은 회원**만 세어야 한다.

| 선택지 | 쉬운 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 탈퇴하지 않은 줄에만 중복 불가를 건다** | PostgreSQL의 부분 인덱스(`WHERE deleted_at IS NULL`)를 쓴다 | 표 구조를 거의 안 바꾼다. PostgreSQL이면 가능 | MySQL로 바꾸면 쓸 수 없다 |
| B. 탈퇴할 때 이메일·닉네임을 지우거나 바꾼다 | 탈퇴한 줄은 `deleted-123@…` 같은 값으로 바꾼다 | 어떤 DB에서나 된다 | 탈퇴 처리 코드가 늘어난다 |
| C. 탈퇴하면 줄을 실제로 지운다 | soft delete를 안 쓴다 | 가장 단순하다 | 다른 사람 글에 단 댓글의 "탈퇴한 사용자" 표시 방법을 따로 정해야 한다 |

- **추천**: **A** (DB가 PostgreSQL 가안이므로). 대소문자는 소문자로 맞춘 값으로 비교한다.
- **영향**: 팀 ERD 변경. `002` 계정 관리 plan에서도 같은 결정이 쓰인다.

### D-5. 암호화된 연결(HTTPS)과 배포 환경 — `미정` (FR-036, NF-04, NF-10)

- 배포 환경이 정해지지 않았다. (기술스택-아키텍처 5장) 그래서 FR-036은 **배포 때 확인할 항목**으로 두고, `Secure` 쿠키 속성도 배포 설정에서만 켠다.
- **개발 중**: HTTP로 해도 된다. 화면 개발 서버의 프록시로 화면과 서버를 같은 주소처럼 만든다. (상세/01 `개발 환경`)
- **선택지**는 배포 환경을 정할 때 같이 보여 준다. 지금은 정하지 않는다.

### D-6. Redis를 어디까지 쓸까 (헌법 해석) — **결정됨 (2026-10-07)**

> **결정 (2026-10-07)**: 헌법을 1.1.0으로 개정해 Redis를 "잃어도 되는 짧은 값"에 쓸 수 있게 했다. 이 기능의 인증 흐름 값(틀린 횟수, 재발송 제한, 인증 완료 표시)은 허용 목록에 들어 있다. 로그인 잠금은 계속 Redis에 두지 않는다(D-3).

- **헌법의 문구**: "Redis는 **이메일 인증번호 저장에만** 쓴다"
- **`상세/01`이 이미 적어 둔 것**: 인증번호 외에도 **틀린 횟수, 다시 받기 제한(1분·하루), 인증 완료 표시**를 Redis에 둔다. 모두 같은 이메일 인증 흐름에서 쓰고 시간이 지나면 사라지는 값이다.
- **판단 (확인 요청)**: 이 값들을 **"이메일 인증번호 저장"의 일부로 본다.** 같은 목적이고, 따로 두면 오히려 단순함이 사라진다. 이 해석이 맞는지 확인이 필요하다. 아니라고 하면 이 값들을 PostgreSQL로 옮기고 정리 작업을 더한다. (대안)
- 같은 이유로 **로그인 잠금은 Redis에 두지 않기로** 했다. (D-3 결정)
- 다른 기능에서의 Redis 사용(조회수 중복 방지 등)은 그 기능의 plan에서 따로 확정한다. (기술스택-아키텍처 2.4)
