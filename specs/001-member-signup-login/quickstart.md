# Quickstart: 회원 가입과 로그인 확인 시나리오

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Contract**: [contracts/auth-api.md](contracts/auth-api.md) | **Date**: 2026-10-07

> 구현이 끝났을 때 **이 기능이 제대로 동작하는지 처음부터 끝까지 확인하는 순서**입니다. 코드는 아직 없으므로 실행 명령은 적지 않았습니다. 프로젝트 저장소가 생기면 `준비`의 빈칸을 채웁니다.
> 각 시나리오에는 연결된 사용자 이야기(US), 요구사항(FR), 성공 기준(SC)을 적었습니다. 모든 SC가 어느 시나리오에서 확인되는지는 마지막 표에 있습니다.

## 준비

| 필요한 것 | 내용 | 비고 |
|---|---|---|
| PostgreSQL, Redis | 개발용으로 띄운다 | 방법은 [가이드/03-로컬환경-도커컴포즈-사용법.md](../../docs/4-가이드/03-로컬환경-도커컴포즈-사용법.md)를 따른다 |
| 서버 | 개발용 설정으로 실행한다 | 실행 명령은 구현 뒤에 채운다 |
| 메일 | 실제로 보내지 않고 **서버 로그에 인증번호를 출력**한다 | 개발용 설정에서만 (`research.md` B-9). 실제 발송은 `D-1`이 정해진 뒤 |
| 확인 도구 | 화면, 또는 API 도구(예: curl, Postman) | 변경 요청(POST)은 먼저 `GET /api/auth/csrf`로 받은 토큰을 헤더에 싣는다 |
| 시간 줄이기 | 테스트용 설정에서 시간을 짧게 바꾼다 | 예: `code-ttl` 10초, `idle-timeout` 1분, `absolute-timeout` 2분, `lock-duration` 30초. 이름은 [plan.md](plan.md)의 `설정값 목록` |
| 테스트 계정 | 시나리오마다 **새 이메일**을 쓴다 | 같은 이메일을 다시 쓰려면 DB에서 지우거나 소문자로 같은 값이 되지 않게 바꾼다 |

## S-1. 가입 정상 흐름 (US1)

연결: US1-1 ~ 3, FR-001, 002, 011, 013 ~ 016, SC-001, SC-006

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | 새 이메일과 규칙에 맞는 닉네임으로 `인증번호 받기` | "인증번호를 보냈습니다. 10분 안에 입력해 주세요". 서버 로그에 6자리 번호가 찍힌다. 번호에 `O`, `0`, `I`, `1`이 없다 |
| 2 | 로그에 나온 번호로 `확인` | "이메일 인증이 완료되었습니다" |
| 3 | 규칙에 맞는 비밀번호로 `가입하기` | "가입이 완료되었습니다. 로그인해 주세요" |
| 4 | DB에서 회원, 블로그, 분류를 본다 | 회원 한 줄. 블로그 이름이 `{닉네임}의 블로그`, 분류 `미분류` 한 줄 |
| 5 | **사람이 직접** 처음부터 끝까지 시간을 잰다 (SC-006 제안값) | 5분 안에 끝난다 |

## S-2. 인증 없이는 가입할 수 없다 (US1-5)

연결: FR-002, FR-022, FR-034, SC-001

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | 인증번호를 받지 않은 이메일로 화면을 거치지 않고 `POST /api/auth/signup`을 보낸다 | `403` "이메일 인증을 먼저 완료해 주세요". 회원이 만들어지지 않는다 |
| 2 | 인증을 마친 뒤 **인증됨 표시 시간(30분)을 줄인 설정**으로 시간이 지나기를 기다렸다 가입한다 | "인증 유효 시간이 지났습니다. 이메일 인증을 다시 해 주세요" (또는 계약의 `EMAIL_NOT_VERIFIED`) |
| 3 | 이메일 인증을 마친 뒤 `이메일 변경`(`cancel`)을 하고 같은 이메일로 가입한다 | 거절된다 |
| 4 | 가입이 끝난 뒤 같은 이메일로 **같은 요청을 다시** 보낸다 | 거절된다 (인증됨 표시가 지워졌고 이미 가입됨) |

## S-3. 인증번호 규칙 (US1 Edge Cases)

연결: FR-016 ~ 021, NF-05

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | 번호를 받고 **유효 시간을 줄인 설정**으로 기다린 뒤 입력 | "인증번호가 만료되었습니다. 인증번호를 다시 받아 주세요" |
| 2 | 번호를 받고 **틀린 번호를 연속 5번** 입력 | 5번째 응답이 "인증번호 입력 횟수를 초과했습니다…". 이후에는 맞는 번호도 거절된다 |
| 3 | 맞는 번호를 입력해 인증한 뒤, **같은 번호를 다시** 입력 | 쓸 수 없다 (1회용) |
| 4 | 번호를 받고, 곧바로 다시 받은 뒤, **첫 번째 번호**를 입력 | 거절된다 (이전 번호 무효) |
| 5 | 번호를 받고 1분 안에 다시 받는다 | "잠시 뒤에 다시 요청해 주세요" |
| 6 | 1분씩 기다리며 5번 받은 뒤 6번째를 요청한다 | "오늘은 더 이상 인증번호를 보낼 수 없습니다" |
| 7 | **메일 발송이 실패하도록** 만든 뒤(개발용 설정에서 발송 오류를 일으킴) 받기를 누른다 | "메일을 보내지 못했습니다. 잠시 뒤 다시 시도해 주세요". **바로 다시 받기를 누를 수 있다** (1분 제한에 걸리지 않는다) |
| 8 | 이미 가입된 이메일로 받기를 누른다 | "이미 가입된 이메일입니다". 서버 로그에 번호가 찍히지 않는다 (메일을 보내지 않음) |

## S-4. 중복 가입은 한 건도 생기지 않는다 (US1, SC-002)

연결: FR-003, FR-004, FR-005, FR-012, FR-023, SC-002

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | `Abc@x.com`으로 가입한 뒤 `abc@x.com`으로 받기 | "이미 가입된 이메일입니다" |
| 2 | 닉네임 `Kim`으로 가입한 뒤 `kim`으로 가입 시도 | "이미 사용 중인 닉네임입니다" |
| 3 | 같은 이메일로 인증을 마친 **두 사람**(두 요청)이 가입을 거의 동시에 보낸다 | 한 건만 성공한다. DB에 같은 이메일 회원이 하나다 |
| 4 | `가입하기`를 연속으로 여러 번 누른다 (요청 여러 개를 동시에) | 한 번만 처리된다 |
| 5 | 서버 코드의 사전 검사를 거치지 않고 DB에 같은 이메일을 직접 넣어 본다 | DB가 거절한다 (마지막 방어선) |

## S-5. 로그인과 로그아웃 (US2)

연결: FR-024 ~ 026, FR-031, FR-032, SC-003

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | 올바른 이메일과 비밀번호로 로그인 | `200`과 세션 쿠키. 화면은 보던 화면(또는 첫 화면)으로 이동 |
| 2 | 없는 이메일로 로그인 | "이메일 또는 비밀번호가 올바르지 않습니다" |
| 3 | 있는 이메일에 틀린 비밀번호로 로그인 | **2번과 똑같은** 문구와 응답 모양 (SC-003) |
| 4 | 이메일 또는 비밀번호를 비우고 로그인 | 입력 오류. 실패 횟수가 늘지 않는다 |
| 5 | **로그인 전**의 쿠키(세션 값)를 기억해 두고 로그인한 뒤 쿠키를 비교 | 값이 바뀌었다 (FR-032) |
| 6 | 로그아웃 | 바로 로그인 전 상태. 이전 쿠키로 `GET /api/auth/me` | `401` |
| 7 | 가입한 직후 로그인 | 가입을 마친 계정은 바로 로그인된다 (FR-011) |

## S-6. 로그인 유지 (US2-3, US2-5)

연결: FR-030, SC-005, `research.md` R-1, R-2

> 시간을 줄인 설정(예: `idle-timeout` 1분, `absolute-timeout` 2분)으로 확인한다.

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | 로그인하고 브라우저를 닫았다가 **유지 시간 안에** 다시 열어 `GET /api/auth/me` | 로그인 상태 (`200`) |
| 2 | 로그인한 뒤 **유지 시간보다 오래** 아무것도 하지 않고 `GET /api/auth/me` | `401` |
| 3 | 유지 시간 안에 계속 요청을 보내며 **절대 유지 시간(30일에 해당)** 이 지나기를 기다린다 | 계속 쓰고 있어도 절대 시간이 지나면 `401` |
| 4 | **(R-1)** 브라우저 도구로 쿠키의 만료 시각을 로그인 직후와 여러 번 요청한 뒤에 비교한다 | 요청을 계속하면 쿠키 만료 시각도 뒤로 밀린다. 안 밀리면 로그인한 지 7일 뒤에 풀리므로 `plan.md`의 R-1 대안(쿠키를 다시 내려 주는 장치)을 적용한다 |
| 5 | 서버를 껐다 켠 뒤 `GET /api/auth/me` | 로그인이 유지된다 (세션이 PostgreSQL에 있음) |

## S-7. 5회 실패 잠금 (US3)

연결: FR-027 ~ 029, SC-004

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | 같은 계정으로 틀린 비밀번호로 4번 로그인 | 매번 일반 실패 문구. **남은 횟수는 어디에도 보이지 않는다** |
| 2 | 5번째 틀림 | "로그인 시도가 5회 실패해 잠겼습니다. {N}분 뒤에 다시 시도해 주세요" |
| 3 | **올바른** 비밀번호로 로그인 | 로그인되지 않고 남은 시간이 보인다 |
| 4 | 잠금 시간(줄인 설정)이 지난 뒤 올바른 비밀번호로 로그인 | 로그인된다. 실패 횟수가 0으로 돌아간다 |
| 5 | 3번 틀린 뒤 올바른 비밀번호로 로그인하고, 다시 4번 틀리기 | 잠기지 않는다 (성공하면 횟수가 0) |
| 6 | **없는 이메일**로 10번 로그인 | 항상 일반 실패 문구. 잠금 문구는 나오지 않고 DB에 기록이 늘지 않는다 |
| 7 | 같은 계정으로 틀린 비밀번호 요청 5개를 **동시에** 보낸다 | 5회 안에 잠긴다 (실패 횟수가 정확히 올라간다) |

## S-8. 로그인으로 안내 (US4)

연결: FR-033

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | 로그아웃한 상태에서 회원 전용 기능(글쓰기 등)의 요청을 보낸다 | `401 UNAUTHENTICATED` |
| 2 | 화면에서 `글쓰기`를 누른다 | 로그인 창이 뜬다 |
| 3 | 로그인 창에서 로그인한다 | 하려던 글쓰기 화면으로 돌아간다 |

> 회원 전용 기능은 다른 기능(`003` 이후)이 만들어져야 눌러 볼 수 있다. 그 전에는 `GET /api/auth/me`의 `401`과 화면의 로그인 창 동작만 확인한다.

## S-9. 보안 점검 (공통)

연결: FR-010, FR-032, FR-034, FR-035, NF-01, NF-06, NF-10, NF-11

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | DB의 회원 표에서 비밀번호 칸을 본다 | 원문이 아니라 해시다. 같은 비밀번호로 가입한 두 회원의 값이 서로 다르다 |
| 2 | 서버 로그와 오류 응답에서 방금 쓴 비밀번호를 검색한다 | 어디에도 없다 |
| 3 | 로그인 응답의 쿠키 속성을 본다 | `HttpOnly`가 있다. `SameSite`가 있다. (`Secure`는 배포에서만) |
| 4 | **CSRF 토큰 없이** `POST /api/auth/login`을 보낸다 | 거절된다 |
| 5 | 이상한 요청(잘못된 JSON, 아주 긴 값, 없는 주소)을 보낸다 | 오류 응답에 예외 이름, 쿼리, 파일 경로가 없다 |
| 6 | 닉네임이나 이메일에 `' OR 1=1 --` 같은 값을 넣는다 | 형식 오류로 거절되고 DB가 바뀌지 않는다 |
| 7 | 화면을 거치지 않고 규칙을 어긴 값(7자 비밀번호, 11자 닉네임)을 직접 보낸다 | 서버가 거절한다 (FR-034) |

## S-10. Redis가 꺼졌을 때

연결: `research.md` D-6, 기술스택-아키텍처 2.4

| # | 한다 | 기대한다 |
|---|---|---|
| 1 | Redis를 끈다 | — |
| 2 | `인증번호 받기` | "잠시 뒤 다시 시도해 주세요" (`SERVICE_UNAVAILABLE`). 서버가 죽지 않는다 |
| 3 | 이미 가입한 회원이 로그인한다 | **정상적으로 로그인된다** (세션은 PostgreSQL, 잠금은 회원 표) |
