# MyBlog Constitution

> 프로젝트 이름은 임시입니다. 이 문서는 `CLAUDE.md`의 작업 규칙과 `docs/`의 확정된 결정을 Spec Kit의 프로젝트 원칙 형식으로 옮긴 것입니다.

## Core Principles

### I. 무엇을 먼저, 어떻게는 나중에 (NON-NEGOTIABLE)

요구사항과 명세(spec)에는 **"무엇을 할 수 있어야 하는가"만** 적는다(MUST). 기술 이름, 라이브러리, 색·모양 같은 디자인 상세는 적지 않는다(MUST NOT). 기술은 계획(plan)과 각 상세 문서의 `구현 방식`에만 적고, 기술마다 **어느 요구사항 ID를 위한 것인지** 연결한다(MUST).

적을지 말지는 "이 줄이 없으면 만드는 사람이 다르게 만들 수 있나?"로 정한다.

*이유: 같은 요구사항을 보고 사람마다 다르게 만드는 일을 막고, 기술이 바뀌어도 요구사항은 흔들리지 않게 하기 위해서다.*

### II. 정하지 않은 것은 임의로 정하지 않는다

모든 기술 항목에는 상태를 `확정` / `가안`(바뀔 수 있음) / `미정` 중 하나로 표시한다(MUST). 미정 항목은 **선택지, 추천안, 이유**를 보여 주고, 사용자가 고르기 전에는 확정하지 않는다(MUST NOT). 모호한 요구사항은 추측으로 채우지 않고 `[NEEDS CLARIFICATION]`으로 표시한다(MUST).

고른 기술이 요구사항을 지키기 어렵게 만들면 바로 알린다. (예: 세션을 서버 메모리에만 두면 "7일 유지" 요구를 지킬 수 없다.)

*이유: 신입 개발자가 AI와 함께 진행하는 프로젝트이므로, 결정은 사람이 하고 AI는 근거와 선택지를 제공한다.*

### III. 쉬운 설명 우선

기술 문서는 비전공자 팀원도 읽을 수 있게 **쉬운 설명을 먼저** 쓰고, 고른 이유와 대안, 쓰지 않는 이유를 함께 적는다(MUST).

*이유: 팀원 4명이 같은 문서를 보고 합의하려면 모두가 이해할 수 있어야 한다.*

### IV. 보안 기본기 (NON-NEGOTIABLE)

- 비밀번호는 원문으로 저장하지 않는다. 단방향 해시를 쓴다(MUST). 해시 방식(BCrypt 추천)은 가안이다.
- 권한 검사(예: 글은 작성자 본인만 수정·삭제)는 **서버에서** 한다(MUST). 화면에서만 막지 않는다.
- 입력 검증(글자 수, 형식, 필수 여부)은 **서버에서** 한다(MUST). 화면 검사는 보조다.
- 본문과 댓글의 스크립트는 실행되지 않아야 하고, 입력값으로 데이터베이스를 조작할 수 없어야 한다(MUST). 쿼리는 문자열을 이어 붙여 만들지 않는다(MUST NOT).

*이유: 화면은 우회할 수 있으므로, 지켜야 하는 규칙은 서버가 마지막 방어선이다.*

### V. 단순하게, MVP 먼저

- 서버는 **단일 서버**로 만들고 안은 기능별 모듈로 나눈다. MSA는 하지 않는다(MUST NOT).
- RabbitMQ 같은 메시지 큐는 쓰지 않는다(MUST NOT). 비동기 처리는 `@Async`, `@Scheduled`로 충분하다.
- 외부 서비스(API) 연동은 하지 않는다. 예외는 **인증 메일 발송(SMTP)**이다. AI 호출을 예외로 할지는 미정이다.
- 새 아이디어는 바로 MVP에 넣지 않고 **"추후 확장 후보"**에 모은다(MUST).

*이유: 범위가 커지면 끝낼 수 없다. 필요가 생길 때 더하는 편이 안전하다.*

### VI. 설정값은 한곳에서

글자 수 제한, 용량, 잠금 시간 같은 **기본값은 한곳에서 바꿀 수 있어야** 한다(MUST). 문서에서는 각 상세 파일의 `기본값` 표에 적고, 숫자를 바꾸면 **본문과 `기본값` 표를 같이** 고친다(MUST).

*이유: 숫자가 코드와 문서 여러 곳에 흩어지면 서로 어긋난다.*

## 기술 제약

**확정** (바꾸려면 헌법 개정이 필요하다)
- 서버 구조: 단일 서버
- 인증 방식: 서버 세션(쿠키). 세션은 PostgreSQL에 저장(Spring Session JDBC). JWT는 쓰지 않는다.
- Redis: **잃어도 되는 짧은 값에만** 쓴다. 만료 시간이 되면 자동 삭제된다. 허용하는 것은 이메일 인증 흐름의 값(인증번호, 틀린 횟수, 재발송 제한, 인증 완료 표시)과 조회수 중복 방지·오늘 방문 표시(가안)뿐이다. 로그인 세션, 로그인 잠금, 오래 남아야 하는 데이터는 두지 않는다(MUST NOT). 새 용도를 더하려면 이 줄을 먼저 개정한다.

**가안** (바뀔 수 있다. 바꿀 때는 plan에 이유와 영향받는 요구사항 ID를 적는다)
- 서버: Spring Boot (Java), Spring Security
- 화면: React (Vite)
- DB: PostgreSQL
- 통신: REST API (JSON)
- 인증번호 메일: SMTP (Spring Mail). **가입 전에** 인증한다.

**미정** (정하기 전에 선택지와 추천안을 먼저 보여 준다)
- SMTP 발송 계정, 이미지 저장 위치, 배포 환경

**용어**: *주제*는 **글마다** 고르는 서비스 전체의 분류(여행, 음식, 취미, 운동, 개발)이고, *카테고리(분류)*는 한 블로그 안에서 주인이 만드는 분류다. 섞어 쓰지 않는다.

## 작업 흐름

- **변경 전 확인**: 파일을 바꾸기 전에 무엇을 바꿀지 먼저 설명하고 확인받는다(MUST). 읽기와 조회는 확인 없이 해도 된다.
- **진행 순서**: 요구사항 → 기술 스택 → 시스템 아키텍처 → ERD → API 명세서 → 구현. Spec Kit에서는 `specify`(요구사항) → `plan`(기술 스택, 아키텍처, ERD, API) → `tasks` → `implement`에 대응한다.
- **팀 문서 보호**: `요구사항-공통.md`와 `요구사항-비교표.md`는 팀 합의용이므로 합의 없이 고치지 않는다(MUST NOT).
- **두 곳이 같이 바뀐다**: 기술 내용은 `docs/2-요구사항/상세/`의 `구현 방식`과 `기술스택-아키텍처.md`에만 적고, 한쪽을 고치면 다른 쪽도 확인한다. 규칙을 더하거나 옮기면 `00-목차.md`의 ID 목록도 확인한다.
- **문서 형식**: 팀원 문서에 맞춰 기능 ID, 표 구조, 상태 표기(화면 있음 / 데모 / 화면 없음)를 쓴다.
- **알림**: 빠진 부분, 충돌하는 부분, 예외 상황이 보이면 질문이나 제안으로 알린다.

## Governance

이 헌법은 다른 작업 방식보다 우선한다. 개정은 **변경 제안 → 이유 설명 → 사용자 확인 → 반영과 버전 올림** 순서로 하며, 확인 없이 고치지 않는다.

- **버전 규칙**: MAJOR는 원칙의 삭제나 재정의, MINOR는 원칙이나 섹션의 추가·확장, PATCH는 문구 정리다.
- **준수 확인**: spec, plan, tasks를 만들 때마다 이 헌법과 어긋나는지 확인한다. 어긋나면 이유를 적고 사용자 확인을 받는다.
- **실행 지침**: 프로젝트 폴더의 `CLAUDE.md`를 따른다.
